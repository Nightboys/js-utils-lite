# `create-nightboy` 多模板脚手架设计

## 1. 背景与目标

当前项目是已发布的 JavaScript 工具包 `@nightboy/js-utils-lite`。本次在当前工作区内新增独立 npm 包 `create-nightboy`，用于通过交互向导或命令参数生成具备常用业务基础设施的前端、Node.js 和 npm 工具库项目。

脚手架的首版目标如下：

- 提供 Vue、React、Node.js 和 npm 工具库共 6 种模板。
- 同时支持交互向导和完整的命令参数调用。
- 支持 npm、pnpm 和 yarn。
- 支持选择是否安装依赖、是否初始化 Git。
- 本地模板随 npm 包发布，默认生成过程不依赖网络下载模板。
- 实现默认关闭的远程 Git 模板源，通过统一接口与本地模板源显式切换。
- 对目录覆盖、临时文件和子进程执行实施明确的安全保护。

首版实现但不默认启用六个独立 Git 仓库模板源；不实现命令行自定义模板地址、插件系统、缓存、自动回退和模板在线更新。

## 2. 包定位与运行环境

脚手架作为独立发布单元放置在当前工作区：

```text
packages/create-nightboy/
```

包名为 `create-nightboy`，命令名同为 `create-nightboy`，用户可通过以下方式运行：

```bash
npm create nightboy@latest
npx create-nightboy
```

脚手架采用 ESM，最低支持 Node.js 18。生成的所有项目也以 Node.js 18 作为最低运行环境。

CLI 运行依赖控制在以下范围：

- `commander`：命令参数解析和帮助信息。
- `@inquirer/prompts`：交互式问答、确认和取消处理。
- `picocolors`：终端状态、警告和错误文本着色。
- Node.js 原生模块：文件操作、路径校验、临时目录和子进程执行。

独立包的发布清单必须显式声明：

- `bin.create-nightboy` 指向 `bin/create-nightboy.js`，且入口文件具备可执行权限和 Node shebang。
- `files` 至少包含 `bin`、`src`、`templates`、`README.md` 和 `LICENSE`。
- `engines.node` 为 `>=18`。
- `type` 为 `module`。

发布包冒烟测试必须从生成的 tarball 安装，确认命令入口可执行，并验证 6 个本地模板均包含在包内。

## 3. 总体架构

脚手架按职责拆分为参数入口、交互补全、模板源、项目生成、目录安全和外部命令执行模块：

```text
packages/create-nightboy/
├── bin/
│   └── create-nightboy.js
├── src/
│   ├── cli.js
│   ├── prompts.js
│   ├── create-project.js
│   ├── package-manager.js
│   ├── safety.js
│   └── template-sources/
│       ├── index.js
│       ├── local.js
│       ├── metadata.js
│       └── remote.js
├── templates/
│   ├── vue/
│   ├── vue-ts/
│   ├── react/
│   ├── react-ts/
│   ├── node-ts/
│   └── library-ts/
├── test/
└── package.json
```

各模块职责如下：

- `bin/create-nightboy.js`：仅负责启动 CLI、设置退出码和处理顶层异常。
- `cli.js`：定义命令参数，合并参数与交互结果，编排完整生成流程。
- `prompts.js`：收集缺失选项，处理用户取消和覆盖确认。
- `create-project.js`：生成临时项目、替换变量、迁移到目标目录并输出结果。
- `package-manager.js`：检测包管理器，生成安装与启动命令，通过参数数组执行子进程。
- `safety.js`：校验项目名、解析目标路径、识别受保护路径和判断目录状态。
- `template-sources/index.js`：定义模板源统一入口并选择当前实现。
- `template-sources/local.js`：列出和物化随包发布的本地模板。
- `template-sources/remote.js`：维护六个独立 Git 仓库地址，并通过浅克隆物化远程模板。
- `template-sources/metadata.js`：维护本地源和远程源共用的模板元数据，避免两套来源产生标识与转换规则漂移。

`create-project.js` 不直接读取 `templates` 目录，只通过模板源提供的接口工作。首版模板源最小契约为：

```js
listTemplates(): Promise<TemplateMetadata[]>
materializeTemplate(templateId, destination): Promise<void>
```

`materializeTemplate()` 的 `destination` 由调用方预先创建，调用时必须是空目录。模板源只能写入该目录内部；成功后该目录本身就是模板根目录，不得额外嵌套仓库名或保留 `.git`。目标目录非空、模板 ID 未知或物化失败时必须抛出错误；失败过程中允许留下部分内容，由 `createProject()` 统一删除整个临时目录，不迁移到最终目标。

`TemplateMetadata` 是模板源与生成器之间的公开数据契约，至少包含：

```js
{
  id: 'vue-ts',
  label: 'Vue 3 + Vite + TypeScript',
  category: 'frontend',
  language: 'typescript',
  renameFiles: { '_gitignore': '.gitignore' },
  textFiles: ['README.md'],
  requiredVariables: ['projectName']
}
```

`id`、`label`、`category` 和 `language` 用于选择与展示；`renameFiles`、`textFiles` 和 `requiredVariables` 定义物化后的转换协议。模板源负责维护并返回这些元数据，`create-project.js` 负责按元数据执行重命名、结构化修改和文本变量替换。所有路径均相对于物化目录，禁止绝对路径和 `..` 路径片段。

文本变量统一使用 `{{variableName}}` 语法。首版仅允许 `{{projectName}}`，只扫描 `textFiles` 登记的 UTF-8 文本文件；`package.json.name` 始终通过 JSON API 修改，不登记为文本替换目标。转换完成后，生成器扫描所有登记文本文件并拒绝遗留的 `{{...}}` 占位符。

远程模板源实现相同契约，每个模板对应一个独立 Git 仓库，仓库根目录就是模板根目录。物化时使用 `git clone --depth 1 <repositoryUrl> <destination>` 克隆仓库默认分支；该命令允许目标目录已存在，但目标目录必须为空。克隆成功后先移除 `.git` 元数据，再执行任何文件重命名、`package.json` 修改或文本变量替换。

远程模板进入转换流程前必须递归拒绝全部符号链接，并对元数据声明的源路径、目标路径和文本文件执行真实路径边界校验，确保解析结果仍位于物化目录内。必须存在可解析为 JSON 对象的 `package.json` 和普通文件 `README.md`。ESLint 禁入校验覆盖文件名包含 `eslint` 的配置或忽略文件、`package.json` 中名称包含 `eslint` 的 `dependencies` / `devDependencies`、名称为 `eslintConfig` 的配置字段，以及名称或命令包含 `lint` / `eslint` 的脚本；发现任一残留即物化失败。

Git 不可用、仓库不可访问、克隆中断或模板校验失败时直接报错，不静默回退本地模板。远程模式刻意跟随仓库默认分支，因此接受同一脚手架版本在不同时间生成不同远程模板；已发布脚手架版本可重复生成相同依赖清单的承诺仅适用于默认的内置本地模板。未来若需要远程可复现性，再为六仓库映射增加固定 commit 或 tag。

模板来源由 `template-sources/index.js` 显式控制：默认返回本地源，同时保留相邻的远程源切换语句。启用远程时只需替换 `remote.js` 中六个仓库地址，并在 `index.js` 将返回值切换为远程源；CLI 收集参数和项目生成主流程无需修改。

## 4. 命令接口与交互流程

### 4.1 调用方式

脚手架支持纯交互和参数驱动两种模式：

```bash
npm create nightboy@latest
npm create nightboy@latest my-app -- --template vue-ts
npm create nightboy@latest api-service -- --template node-ts --package-manager pnpm --no-install
```

### 4.2 参数定义

| 参数 | 说明 |
| --- | --- |
| `[project-name]` | 项目名称，同时作为默认目录名和 `package.json.name` |
| `-t, --template <id>` | 指定模板标识 |
| `-p, --package-manager <name>` | 指定 npm、pnpm 或 yarn |
| `--install` / `--no-install` | 是否在生成后安装依赖 |
| `--git` / `--no-git` | 是否在生成后初始化 Git |
| `--force` | 允许清空已校验的非空目标目录 |
| `--help` | 显示帮助信息 |
| `--version` | 显示脚手架版本 |

模板标识固定为：

- `vue`
- `vue-ts`
- `react`
- `react-ts`
- `node-ts`
- `library-ts`

### 4.3 参数与交互合并规则

CLI 优先使用用户显式传入的参数，只对缺失项发起交互问答。是否可以交互由 `stdin.isTTY && stdout.isTTY` 决定，而不是由用户是否传入过参数决定。因此，传入部分参数的混合调用仍属于可交互调用。向导依次收集：

1. 项目名称。
2. 模板。
3. 包管理器。
4. 是否安装依赖。
5. 是否初始化 Git。

选项在解析阶段保留“未指定”状态，不提前把布尔选项折叠成默认值。在可交互环境中，所有未指定项均通过向导收集。在非交互环境中不得等待输入，并采用以下确定性规则：

- `project-name` 和 `--template` 必须显式提供，缺少任一项即返回输入错误。
- 未提供 `--package-manager` 时使用 `npm`。
- 未提供 `--install` 或 `--no-install` 时默认安装依赖。
- 未提供 `--git` 或 `--no-git` 时默认初始化 Git。

显式参数始终覆盖交互或非交互默认值。`--force` 在任何环境中都表示已经授予非空目标目录覆盖权，不再二次询问；没有 `--force` 时，可交互环境必须确认，非交互环境必须中止。

用户通过 `Ctrl+C` 或提示组件的取消能力终止操作时，CLI 视为主动取消：不输出错误堆栈，清理临时目录，并以退出码 `130` 结束。

## 5. 项目生成流程

生成流程分为准备、物化、提交和可选后处理四个阶段：

1. 解析命令参数并通过向导补齐缺失项。
2. 校验项目名称、模板标识、包管理器和目标绝对路径。
3. 检查目标目录状态，并根据交互确认或 `--force` 判断是否允许覆盖。
4. 检测所选包管理器是否存在。用户选择安装依赖时，缺失的包管理器属于阻断错误。
5. 在目标目录的父级创建唯一临时目录。
6. 模板源将指定模板完整物化到临时目录。
7. 将 `_gitignore` 等 npm 会特殊处理的文件名恢复为正式名称。
8. 使用 JSON 解析和序列化更新 `package.json` 中的项目名称，不对 JSON 使用字符串替换。
9. 对明确登记的文本文件替换少量模板变量，并确认没有遗留占位符。
10. 所有生成检查通过后，将已存在的目标目录原子重命名为同级唯一备份目录，再将同级临时项目原子重命名为目标目录。
11. 根据用户选择安装依赖、初始化 Git。
12. 输出项目路径、进入目录命令和所选包管理器对应的启动命令。

模板复制、变量替换或提交前检查失败时，CLI 清理临时目录，不创建或修改最终目标目录。

目标提交阶段的临时目录、目标目录和备份目录必须位于同一父目录，以便使用同一文件系统内的原子重命名。若临时项目迁移失败，生成器必须先将原目标从备份目录恢复，再清理临时目录；只有恢复完成后才返回错误。新目标迁移成功后才删除备份目录。备份清理失败不回滚已成功生成的项目，但要输出包含备份路径的警告，避免静默遗留。如果原目标无法恢复，CLI 输出高优先级错误和备份绝对路径，不再执行任何后处理。

安装依赖或 Git 初始化发生在项目已经完整生成之后。如果这些步骤失败，保留生成结果并输出失败的程序、参数和可执行的恢复命令，不删除用户已经获得的项目。

## 6. 目录安全策略

所有清理和覆盖操作必须使用标准化后的绝对路径，不允许直接使用未解析的用户输入。

以下路径始终禁止作为生成或清理目标：

- 文件系统根目录。
- 当前用户的主目录。
- CLI 启动时的当前工作目录。
- 解析后不位于当前工作目录之下的任意路径。

目标目录为空时可以直接使用。目标目录非空时执行以下规则：

- 显式传入 `--force` 时无需确认，但仍必须通过全部受保护路径校验。
- 未传入 `--force` 且终端可交互时，要求用户明确确认；拒绝或取消后不修改目录。
- 未传入 `--force` 且终端不可交互时，默认中止。
- 真正执行清理前再次运行保护路径校验，避免检查与执行之间使用了不同路径。

项目名称需要同时满足 npm 包名和安全目录名约束。路径输入不得借助 `..`、绝对路径或符号链接逃逸当前工作目录。对于已经存在的目标目录，应基于真实路径检查符号链接指向；不允许通过符号链接覆盖工作目录外部内容。

## 7. 模板设计

### 7.1 通用约定

所有模板应满足：

- Node.js 18+。
- 包名由脚手架写入，模板不保留真实发布包名。
- 不携带 lockfile，由用户选择的包管理器生成。
- 提供 `README.md`、`.gitignore`、`.env.example` 和基础源码目录。
- 提供开发、构建、测试、格式校验和格式化脚本。
- 使用 Prettier 统一格式，不引入 ESLint。
- 至少包含一个可运行页面或接口，以及对应的基础测试。

模板的直接依赖和开发依赖使用确定的精确版本，不使用 `latest`、`next`、`*` 或无上限范围。更新依赖时统一刷新 6 个模板并执行完整的安装、检查、测试和构建矩阵；已发布脚手架版本内置的本地模板依赖保持不变，以保证本地模式下同一脚手架版本可重复生成相同清单。

模板中的 `.gitignore` 以 `_gitignore` 存储，生成时恢复文件名，防止 npm 打包阶段忽略模板文件。

### 7.2 Vue 模板

`vue` 和 `vue-ts` 使用以下默认技术栈：

- Vite
- Vue 3
- Vue Router
- Pinia
- Axios
- Vitest
- Prettier

模板包含 `src/router`、`src/stores`、`src/services`、首页和 404 页面。Axios 封装提供基础地址、超时配置和统一错误处理；`@` 指向 `src`；样式包含 CSS Reset、颜色变量和布局变量。

JavaScript 与 TypeScript 模板保持相同的业务结构，差异仅限语言、类型配置和必要的构建配置，避免两个模板逐步演变成不同产品。

### 7.3 React 模板

`react` 和 `react-ts` 使用以下默认技术栈：

- Vite
- React
- Wouter（兼容 Node.js 18，避免引入存在已知安全公告的 React Router 6）
- Zustand
- Axios
- Vitest
- Prettier

模板包含 `src/router`、`src/stores`、`src/services`、首页和 404 页面，并使用与 Vue 模板一致的请求层、路径别名、环境变量和样式约定。

### 7.4 Node.js 模板

`node-ts` 使用 Express 和 TypeScript，包含：

- 应用启动与服务器监听分离。
- 环境变量加载和示例配置。
- 路由、控制器和服务分层。
- 健康检查接口。
- 404 与统一错误处理中间件。
- Vitest 接口或模块测试。
- Prettier 和 TypeScript 构建配置。

模板只提供清晰的业务扩展骨架，不首版引入数据库、认证、日志平台或容器部署配置。

### 7.5 npm 工具库模板

`library-ts` 使用 TypeScript，包含：

- ESM 与 CommonJS 双产物。
- TypeScript 类型声明。
- 明确的 `exports` 配置。
- Vitest 单元测试。
- Prettier。
- `npm pack --dry-run` 发布检查。

构建产物不预置在模板中，由生成项目的构建命令产生。

## 8. 包管理器与 Git

首版支持 npm、pnpm 和 yarn。包管理器模块以配置表维护可执行文件、安装参数和常用展示命令，避免在流程中散落条件分支。

依赖安装使用子进程参数数组，不开启 shell，不拼接未经转义的用户输入。子进程继承标准输入输出，使用户能够看到真实安装进度。

Git 初始化仅执行 `git init`，不自动提交，也不修改用户的全局 Git 配置。系统不存在 Git 或初始化失败时，项目仍视为生成成功，但 CLI 输出警告和手动恢复命令。

当依赖安装与 Git 初始化都被选中时，后处理按“安装依赖，再初始化 Git”的顺序执行。安装失败后不再尝试 Git 初始化，保留完整生成项目，输出两项未完成操作的恢复命令，并以退出码 `2` 结束。Git 初始化单独失败时同样保留项目、输出恢复命令并以退出码 `2` 结束。

## 9. 异常与退出行为

错误分为以下类型：

- 输入错误：项目名、模板或包管理器无效，返回用法提示。
- 安全错误：目标路径越界或属于受保护路径，拒绝继续且不允许 `--force` 绕过。
- 冲突错误：非空目录未获得覆盖授权，保持目录不变。
- 模板错误：模板不存在、复制失败或占位符未替换，清理临时目录。
- 后处理错误：安装或 Git 初始化失败，保留项目并给出恢复步骤。
- 用户取消：清理临时目录，不输出内部堆栈。

默认日志只展示用户可以采取行动的信息。调试堆栈不作为首版公开参数的必要能力；无法识别的顶层错误可以打印精简错误信息并返回非零退出码。

CLI 退出码固定为：

| 退出码 | 含义 |
| --- | --- |
| `0` | 项目生成及所有选中的后处理步骤成功 |
| `1` | 输入、安全、目录冲突、模板或未知错误，最终项目未成功生成 |
| `2` | 项目已完整生成，但依赖安装或 Git 初始化失败 |
| `130` | 用户主动取消或终端中断 |

包管理器缺失发生在提交目标目录之前，因此属于退出码 `1`；安装过程中失败发生在项目生成之后，因此属于退出码 `2`。

## 10. 测试与发布验证

### 10.1 单元测试

使用 Node.js 内置测试运行器或与包实现一致的轻量测试配置，覆盖：

- CLI 参数解析及默认值合并。
- TTY、非 TTY 和混合参数调用下的补全规则与布尔选项三态行为。
- 项目名称合法性。
- 受保护路径、路径越界、符号链接和非空目录判断。
- 模板元数据及模板源接口。
- npm、pnpm、yarn 的安装和启动命令映射。
- 文件名恢复、JSON 修改和模板变量替换。
- 远程源克隆到已存在空目录并成功清理 `.git`。
- 远程源拒绝非空目录、未知模板 ID、符号链接逃逸和 ESLint 残留。
- Git 缺失、仓库不可达、克隆中断和模板校验失败均抛出错误，且不调用本地模板源。
- `createProject()` 在远程克隆或校验失败后删除整个临时目录，不留下最终目录半成品。

### 10.2 模板生成测试

将 6 个模板分别生成到隔离临时目录，并验证：

- 预期文件存在。
- `_gitignore` 已恢复。
- `package.json.name` 与输入一致。
- 不存在遗留模板占位符。
- `package.json` 脚本和核心依赖符合模板定义。
- JavaScript 与 TypeScript 模板的结构差异符合设计。

### 10.3 CLI 端到端测试

通过临时工作目录执行真实 CLI，至少覆盖：

- 完整参数模式成功生成。
- 缺失必填参数的非交互模式报错。
- 用户取消。
- 空目录、非空目录拒绝和 `--force` 覆盖。
- 禁止覆盖当前目录及工作目录外路径。
- 覆盖提交失败后恢复原目录，并验证备份目录的异常提示。
- `--no-install` 与 `--no-git`。
- 包管理器不存在时的错误处理。
- 安装失败后跳过 Git 初始化，并验证退出码 `2` 和恢复命令。
- 用户取消使用退出码 `130`，生成前错误使用退出码 `1`。

自动测试不得访问真实用户目录、修改真实 Git 配置或依赖全局包管理器状态。外部命令执行通过注入执行器进行单元测试，少量端到端测试只运行环境中确定存在的命令。

### 10.4 发布前检查

发布前依次执行：

1. CLI 单元测试和端到端测试。
2. 逐模板生成检查。
3. 在隔离目录逐模板安装、格式校验、测试和构建。
4. `npm pack --dry-run`，确认 CLI 入口、本地模板和必要文档均进入发布包。
5. 从生成的 tarball 安装并执行一次 CLI 冒烟测试，避免只验证源码目录。

## 11. 文档要求

`create-nightboy` 包需要提供独立 README，至少包含：

- Node.js 版本要求。
- `npm create` 和 `npx` 用法。
- 全部模板及其技术栈。
- 命令参数表。
- 覆盖目录的安全行为。
- 三种包管理器的示例。
- 生成后常用命令。
- 本地开发、测试和发布检查方式。

当前根目录 README 增加工作区内独立脚手架包的入口说明，但不把工具库和脚手架描述为同一个 npm 包。

## 12. 验收标准

满足以下条件时首版视为完成：

- `npm create nightboy@latest` 能启动交互向导。
- 6 个模板都能通过交互或参数模式生成。
- npm、pnpm、yarn 的选择、安装和启动提示正确。
- `--no-install`、`--no-git` 和 `--force` 行为符合设计。
- 受保护目录、工作目录外路径和符号链接逃逸无法被覆盖。
- 生成失败不会留下最终目录半成品，后处理失败会保留完整项目并给出恢复步骤。
- 模板源主流程只依赖统一接口，本地实现可以在不修改 CLI 主流程的情况下替换为远程实现。
- 远程模板源完整实现但默认不启用，替换六个仓库地址并切换 `index.js` 返回值后即可使用。
- 所有自动测试、6 个模板的安装构建验证及发布包冒烟测试通过。

## 13. 后续扩展方向

以下能力不属于首版，但架构应允许后续加入：

- 远程压缩包模板源。
- 企业内部模板注册表和版本固定。
- 通过配置文件新增私有模板。
- `--template-source` 等高级参数。
- 模板缓存、校验和与离线回退。
- 对现有项目执行增量能力安装。
